# ADR-002: localStorage schema v1 + versionado en export/import JSON

## Status
Accepted

## Date
2026-10-20

## Context
La calculadora persiste notas y metas en `localStorage` del navegador. Necesitamos:
- Schema claro y versionado
- Resiliencia ante datos corruptos o schema antiguo
- Backup portable (export/import JSON) para Drive/OneDrive
- Migración futura sin pérdida de datos

## Decision

### 1. localStorage key
```
STORAGE_KEY = 'notas-yeraldine-2026-2'
```
Incluye semestre para aislar entre periodos académicos.

### 2. Schema v1 (actual)
```typescript
interface StorageState {
  notas: Record<string, Record<string, number>>; // { cursoId: { productoId: nota } }
  metas: Record<string, number>;                  // { cursoId: meta }
}
```

Ejemplo:
```json
{
  "notas": {
    "personalidad": { "P1": 15, "P2": 14 },
    "desarrollo": { "P1": 13, "P3-ind": 15, "P3-grup": 16 }
  },
  "metas": {
    "personalidad": 15,
    "desarrollo": 14
  }
}
```

### 3. Carga defensiva (`loadState` en `app.js`)
```javascript
const p = JSON.parse(saved);
state.notas = (p.notas && typeof p.notas === 'object') ? p.notas : {};
state.metas = (p.metas && typeof p.metas === 'object') ? p.metas : {};
```
- Valida que `notas` y `metas` sean objetos
- Si no lo son → reset a `{}` (no rompe la app)
- Log de warning en consola

### 4. Export JSON (backup portable)
```json
{
  "version": "1.0",
  "fecha": "2026-10-20T15:30:00.000Z",
  "semestre": "2026-2",
  "notas": { ... },
  "metas": { ... }
}
```
- `version`: schema version (para migraciones futuras)
- `fecha`: ISO 8601 para auditoría
- `semestre`: redundancia con key localStorage

### 5. Import JSON
- Valida `data.notas` y `data.metas` son objetos
- Sobrescribe estado actual
- Alerta éxito/error al usuario

### 6. Migración futura (v2+)
Cuando cambie schema:
1. Incrementar `version` en export
2. En `loadState`: detectar `data.version` o inferir por estructura
3. Función `migrate(v1 → v2)` que transforme `state.notas` / `state.metas`
4. Guardar estado migrado automáticamente

Ejemplo migración hipotética (añadir campo `comentario` por nota):
```javascript
if (!data.version || data.version === '1.0') {
  // v1 → v2: notas: { cursoId: { prodId: nota } } → { cursoId: { prodId: { nota, comentario } } }
  const migradas = {};
  for (const [cursoId, prods] of Object.entries(data.notas)) {
    migradas[cursoId] = {};
    for (const [prodId, nota] of Object.entries(prods)) {
      migradas[cursoId][prodId] = { nota, comentario: '' };
    }
  }
  data.notas = migradas;
  data.version = '2.0';
}
```

## Alternatives Considered

### IndexedDB
- **Pros:** Más capacidad, queries, transacciones
- **Contras:** Overkill para ~48 notas, API async compleja, no portable a JSON simple

### Cookies
- **Pros:** Sync automático servidor (no aplica)
- **Contras:** 4 KB límite, headers en cada request, no diseñado para esto

### Solo export/import manual (sin localStorage)
- **Pros:** Cero estado persistente
- **Contras:** UX terrible, usuario pierde todo al cerrar pestaña

## Consequences

### Positivas
- **Simple:** 2 objetos planos, serialización nativa JSON
- **Resiliente:** Validación en carga evita crashes por datos corruptos
- **Portable:** JSON abre en cualquier editor, versionado explícito
- **Migrable:** Estrategia clara para v2+

### Negativas
- **Límite 5-10 MB:** Suficiente (datos ~2 KB)
- **Sin sync multi-device:** Por diseño (privacidad, simplicidad)
- **Clearing cache borra datos:** Usuario informado en footer

## Implementation Notes
- `calculations.js` no toca localStorage (pure functions)
- `app.js` es único owner de `state` y `localStorage`
- Tests cubren `loadState` con datos inválidos
